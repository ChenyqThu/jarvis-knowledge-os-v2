# Upstream bug: `gbrain init --migrate-only` fails on real Postgres for multi-statement ADD-COLUMN-then-CREATE-INDEX migrations

- **Status:** reported upstream — garrytan/gbrain#2667 (https://github.com/garrytan/gbrain/issues/2667)
- **Discovered:** 2026-07-07, during fork sync §6.39 (v0.42.53.0 → v0.42.57.0)
- **Affected:** real PostgreSQL engine, schema migrations **v121**
  (`timeline_entries_event_page_id`) and **v122** (`facts_ontology_dimension`),
  both shipped in v0.42.56.0 (Life Chronicle). Also any future migration whose
  single `sql` block adds a column and then creates an index / constraint that
  references that new column.
- **NOT affected:** PGLite engine (tolerates it), and the daemon's `initSchema`
  migration path (which is how our production brain actually reached v122 — see
  "Observed in the wild").

## Symptom

```
$ gbrain init --migrate-only
⚠️  Schema version 119 is behind latest 122.
column "event_page_id" does not exist
```

Deterministic. Schema stays at the pre-migration version (the migration
transaction rolls back cleanly — no partial state).

## Reproducer

Any brain on the real Postgres engine sitting below schema v121, running
`gbrain init --migrate-only` (or otherwise driving `runMigrationSQL` for v121).
v121's `sql` block is:

```sql
ALTER TABLE timeline_entries ADD COLUMN IF NOT EXISTS event_page_id INTEGER;
DO $$ BEGIN IF NOT EXISTS (...) THEN ALTER TABLE timeline_entries
  ADD CONSTRAINT timeline_entries_event_page_id_fkey
  FOREIGN KEY (event_page_id) REFERENCES pages(id) ON DELETE CASCADE; END IF; END $$;
CREATE INDEX IF NOT EXISTS idx_timeline_event_page
  ON timeline_entries(event_page_id) WHERE event_page_id IS NOT NULL;
CREATE UNIQUE INDEX IF NOT EXISTS idx_timeline_event_dedup
  ON timeline_entries(event_page_id, date) WHERE event_page_id IS NOT NULL;
```

v122 has the same shape (`ALTER TABLE facts ADD COLUMN ... dimension/value/
value_hash/dim_status` followed by `CREATE INDEX ... (dimension, ...)`).

The **exact same SQL applies cleanly via `psql`** (verified in a `BEGIN; …
ROLLBACK;` transaction against the live brain — `ALTER TABLE` → `DO` →
`CREATE INDEX` → `CREATE INDEX`, no error).

## Root cause

`runMigrationSQL` (`src/core/migrate.ts`) sends the migration's whole
multi-statement `sql` string to the engine in one call:

- transaction path → `tx.runMigration(m.version, sql)`
- reserved-connection path → `conn.executeRaw(sql)`

both of which land in `PostgresEngine.runUnsafe` → **`conn.unsafe(sql)`**
(`src/core/postgres-engine.ts`, postgres.js). On real PostgreSQL that path
**parse-analyzes the entire multi-statement batch before executing any
statement**, so the `CREATE INDEX … (event_page_id)` is validated *before* the
preceding `ALTER TABLE … ADD COLUMN event_page_id` has run — hence
`column "event_page_id" does not exist`.

- **PGLite** executes statement-by-statement, so it tolerates the intra-batch
  dependency. The chronicle test-suite is PGLite-based
  (`test/migration-v120.test.ts`, `test/chronicle-*.test.ts`), so CI never
  exercised the real-Postgres path for v121/v122. (Same class as the
  v0.42.55.0 hotfix for the `#1385` plpgsql alias collision that "PGLite
  tolerated" but real PG rejected.)
- **`GBRAIN_PREPARE=false` does NOT fix it.** That toggle only disables
  prepared-statement *caching*; `conn.unsafe()` still batch-parses. Confirmed:
  re-running with `GBRAIN_PREPARE=false` (log: "Prepared statements disabled")
  fails identically. The simple-vs-extended distinction that would fix this is
  postgres.js `.simple()`, which `runUnsafe` does not use.

## Observed in the wild (why our production still reached v122)

The daemon (`gbrain serve --http`) runs its own `initSchema` on startup, and
**that path successfully migrated our production brain to a complete, correct
v122** (all v120/v121/v122 objects verified present: `page_links`
`security_invoker=on`, trigger fns `search_path` pinned, `event_page_id` + both
partial indexes, `facts.{dimension,value,value_hash,dim_status}` + both
indexes). So the daemon's schema-init path evidently executes migration SQL
differently from the CLI `--migrate-only` path (statement-by-statement, or a
full schema replay via the born-correct embedded schema). Worth reconciling the
two paths as part of the fix.

## Suggested fix (upstream)

Make `runMigrationSQL` execute each migration's `sql` **statement-by-statement**
(a `DO $$…$$`-aware splitter, or postgres.js `.simple()` for the batch), so an
`ADD COLUMN` commits its catalog change before a later `CREATE INDEX` in the
same migration is parse-analyzed. This matches how PGLite and `psql` already
behave, and how the daemon's initSchema path apparently already behaves.

Alternatively, split each add-column-then-index migration into two ordered
migration entries — but the executor fix is the durable cure (it protects every
future migration of this shape).

## Fork workarounds (if the CLI path is needed before an upstream fix)

1. **Pre-seed the columns** via `psql`, then re-run `gbrain init
   --migrate-only`. Once the columns exist, each `CREATE INDEX` parse-validates
   fine and the `ADD COLUMN IF NOT EXISTS` is a no-op:
   ```sql
   ALTER TABLE timeline_entries ADD COLUMN IF NOT EXISTS event_page_id INTEGER;
   ALTER TABLE facts ADD COLUMN IF NOT EXISTS dimension  TEXT;
   ALTER TABLE facts ADD COLUMN IF NOT EXISTS value      TEXT;
   ALTER TABLE facts ADD COLUMN IF NOT EXISTS value_hash TEXT;
   ALTER TABLE facts ADD COLUMN IF NOT EXISTS dim_status TEXT;
   ```
2. **Let the daemon do it** — restarting `com.jarvis.gbrain-serve-http` onto the
   new binary runs the daemon's initSchema path, which applies the migration
   correctly (this is what happened, accidentally, in §6.39).
3. Full-manual: apply the v120/v121/v122 `sql` blocks via `psql` (simple
   protocol) and `UPDATE config SET value='122' WHERE key='version'`.
